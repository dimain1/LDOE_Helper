# ADR-003: Выбор механизма аутентификации (JWT)

## Статус
Принято

## Контекст

Система требует аутентификации пользователей и разграничения доступа между ролями `USER` и `ADMIN`. Android-клиент работает в мобильной среде с периодическим отсутствием сети. Требуется механизм, не предполагающий серверного хранения активных сессий.

## Решение

Использовать **JWT (JSON Web Tokens)** с двумя типами токенов:
- **Access-токен** — короткоживущий (20 мин, `JWT_ACCESS_EXPIRATION_MS`), передаётся в заголовке `Authorization: Bearer`.
- **Refresh-токен** — долгоживущий (7 дней, `JWT_REFRESH_EXPIRATION_MS`), хранится в таблице `refresh_tokens` на сервере и в защищённом хранилище на клиенте.

## Обоснование

- **Stateless** — сервер не хранит сессии; масштабируется горизонтально.
- Payload JWT содержит роль пользователя → авторизация без дополнительного запроса к БД.
- Удобен для мобильного клиента: токен хранится локально и отправляется с каждым запросом.
- Refresh-токен в БД позволяет инвалидировать сессию при logout (удалением записи).

## Последствия

- Access-токен нельзя отозвать до истечения срока — при компрометации 20-минутное окно уязвимости.
- Таблица `refresh_tokens` требует периодической очистки просроченных записей.
- Секрет JWT (`JWT_SECRET`) должен быть длиной ≥ 32 символа и передаваться через env-переменную.

## Альтернативы

| Альтернатива | Причина отклонения |
|-------------|-------------------|
| Session-based (Cookie) | Требует хранения сессий на сервере; плохо подходит для мобильного клиента |
| OAuth 2.0 / OpenID Connect | Избыточен для однопользовательской системы без сторонних провайдеров |
| API Key | Не поддерживает ролевое разграничение; нет механизма обновления |
