# ADR-001: Выбор архитектурного паттерна (PCMEF)

## Статус
Принято

## Контекст

Система LDOE-Helper включает Android-клиент с UI (в том числе overlay-виджет), бизнес-логикой (события, уведомления, офлайн-режим) и серверную часть с REST API и доступом к БД. Требуется архитектура, обеспечивающая:
- чёткое разделение ответственности между UI, логикой и данными;
- возможность тестировать слои изолированно;
- поддержку нескольких точек входа (основное приложение + overlay-сервис).

## Решение

Применить паттерн **PCMEF** (Presentation – Control – Mediator – Entity – Foundation) в клиент-серверной адаптации:
- **Серверная сторона:** слои Control (REST-контроллеры) → Mediator (сервисы бизнес-логики) → Entity (JPA-сущности) ← Foundation (репозитории).
- **Клиентская сторона:** Presentation (Compose) → ViewModel → Repository → Room / Retrofit.

## Обоснование

- PCMEF чётко разграничивает ответственность: запрос не попадает в репозиторий минуя сервис.
- Слои можно тестировать независимо (mock-репозитории в unit-тестах сервисов).
- Клиент-серверная адаптация позволяет Android-клиенту поддерживать offline-режим без изменения серверной архитектуры.
- Overlay-сервис является отдельным Android Service и взаимодействует с тем же ViewModel — разделение слоёв это упрощает.

## Последствия

- Необходимо реализовать REST API для коммуникации клиент–сервер.
- На Android требуется дополнительный слой Repository, абстрагирующий Room и Retrofit.
- Увеличивается количество классов по сравнению с MVC.

## Альтернативы

| Альтернатива | Причина отклонения |
|-------------|-------------------|
| MVC | Смешивает бизнес-логику с контроллером; плохо масштабируется |
| MVVM (только клиент) | Не описывает серверную сторону; ViewModel не заменяет слой Mediator |
| Clean Architecture | Избыточная сложность для проекта данного масштаба |
