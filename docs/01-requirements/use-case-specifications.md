# Спецификации Use Case

## Описание

Спецификации Use Case — детальные текстовые описания сценариев взаимодействия пользователей с системой. Для каждого прецедента определяются предусловия, постусловия, основной поток, подпотоки и потоки исключений. Документ охватывает ключевые UC высокого приоритета.

---

## UC-001 Поиск информации

**ID:** UC-001  
**Название:** Поиск информации  
**Акторы:** Пользователь  
**Уровень:** Пользовательский  

**1. Краткое описание:**  
Пользователь выполняет поиск игровых объектов по названию или типу в информационной базе приложения.

**2. Предусловие:**
- Пользователь авторизован.
- Данные загружены (из сети или Room-кэша).

**3. Постусловие:**
- Отображён список объектов, соответствующих запросу.

**4. Основной поток:**
1. Пользователь вводит поисковый запрос.
2. Система выполняет поиск в локальном кэше (Room) или обращается к серверу.
3. Система отображает список найденных объектов.
4. Пользователь выбирает объект → переход к UC-002.

**5. Потоки исключений:**

*E1: Совпадений не найдено*
- E1.1. Система отображает сообщение «Ничего не найдено».
- E1.2. Пользователь корректирует запрос.

*E2: Нет подключения и кэш пуст*
- E2.1. Система отображает сообщение об отсутствии данных.

**Приоритет:** Высокий | **Частота:** Часто | **Сложность:** Низкая

## UC-003 Создать событие

**ID:** UC-003  
**Название:** Создать событие  
**Акторы:** Пользователь  
**Уровень:** Пользовательский  

**1. Краткое описание:**  
Пользователь создаёт игровое событие с таймером через основной интерфейс приложения или overlay-виджет, указывая имя события и время срабатывания.

**2. Предусловие:**
- Пользователь авторизован.

**3. Постусловие:**
- Запись о событии сохранена локально (Room).
- Запланировано push-уведомление (WorkManager).

**4. Основной поток:**
1. Пользователь инициирует создание события.
2. Пользователь вводит параметры события (имя, время).
3. Пользователь подтверждает создание.
4. Система валидирует параметры.
5. Система сохраняет запись о событии.
6. Система планирует таймер уведомления.
7. Система отображает подтверждение создания события.

**5. Подпотоки:**

*A: Создание через приложение*
- A1. На шаге 1 инициация происходит в главном интерфейсе приложения.
- A2. Продолжение с шага 2 основного потока.

*B: Создание через overlay-виджет*
- B1. На шаге 1 пользователь нажимает кнопку создания в overlay.
- B2. Открывается компактная форма поверх текущего приложения.
- B3. Продолжение с шага 2 основного потока.

**6. Потоки исключений:**

*E1: Некорректные данные*
- E1.1. На шаге 4 система обнаруживает некорректные параметры.
- E1.2. Система подсвечивает поля с ошибкой и отображает подсказку.
- E1.3. Возврат к шагу 2.

*E2: Ошибка сохранения*
- E2.1. На шаге 5 возникает ошибка записи в Room.
- E2.2. Система уведомляет пользователя об ошибке.
- E2.3. Событие не создаётся.

**Приоритет:** Высокий | **Частота:** Часто | **Сложность:** Средняя

## UC-006 Получить уведомление

**ID:** UC-006  
**Название:** Получить уведомление  
**Акторы:** Пользователь  
**Уровень:** Системный  

**1. Краткое описание:**  
Система автоматически отправляет push-уведомление пользователю при истечении таймера ранее созданного события.

**2. Предусловие:**
- Событие создано и таймер запланирован (WorkManager).
- Android разрешил отправку уведомлений приложению.

**3. Постусловие:**
- Пользователь получил уведомление с названием события.
- Статус события обновлён («сработало»).

**4. Основной поток:**
1. WorkManager запускает фоновую задачу по расписанию.
2. Система извлекает данные события из Room.
3. NotificationManager отображает push-уведомление.
4. Пользователь видит уведомление в шторке Android.
5. При нажатии открывается экран списка событий приложения.

**5. Потоки исключений:**

*E1: Разрешение на уведомления отозвано*
- E1.1. NotificationManager не может отобразить уведомление.
- E1.2. Событие помечается как «сработало» без уведомления.

*E2: Устройство было выключено в момент срабатывания*
- E2.1. WorkManager повторяет задачу при следующем включении устройства.

**Приоритет:** Высокий | **Частота:** Часто | **Сложность:** Средняя

## UC-004 Редактировать событие

**ID:** UC-004  
**Название:** Редактировать событие  
**Акторы:** Пользователь  
**Уровень:** Пользовательский  

**1. Краткое описание:**  
Пользователь изменяет параметры ранее созданного события: название, описание, время начала и окончания.

**2. Предусловие:**
- Пользователь авторизован.
- Событие принадлежит текущему пользователю.

**3. Постусловие:**
- Обновлённые данные события сохранены в Room.
- Таймер уведомления перепланирован с новым временем окончания.

**4. Основной поток:**
1. Пользователь открывает существующее событие.
2. Пользователь изменяет нужные параметры.
3. Пользователь подтверждает изменения.
4. Система валидирует параметры.
5. Система обновляет запись события.
6. Система перепланирует таймер уведомления.
7. Система отображает подтверждение.

**5. Потоки исключений:**

*E1: Некорректные данные*
- E1.1. Система подсвечивает поля с ошибкой.
- E1.2. Возврат к шагу 2.

*E2: Попытка редактирования чужого события*
- E2.1. Сервер возвращает 403 Forbidden.
- E2.2. Прецедент завершается без изменений.

**Приоритет:** Средний | **Частота:** Часто | **Сложность:** Низкая

## UC-014 Создать шаблон

**ID:** UC-014  
**Название:** Создать шаблон  
**Акторы:** Пользователь  
**Уровень:** Пользовательский  

**1. Краткое описание:**  
Пользователь создаёт повторно используемый шаблон события с именем, описанием и стандартной длительностью. Шаблон используется для быстрого создания однотипных событий.

**2. Предусловие:**
- Пользователь авторизован.

**3. Постусловие:**
- Шаблон сохранён на сервере, привязан к создавшему пользователю.
- Шаблон доступен при создании новых событий (UC-003).

**4. Основной поток:**
1. Пользователь инициирует создание шаблона.
2. Пользователь вводит название, длительность (обязательные), описание и изображение (опционально).
3. Пользователь подтверждает создание.
4. Система валидирует данные.
5. Система сохраняет шаблон (multipart: JSON + файл изображения).
6. Система отображает подтверждение с созданным шаблоном.

**5. Потоки исключений:**

*E1: Некорректные данные (пустое имя / отрицательная длительность)*
- E1.1. Система возвращает ошибку валидации.
- E1.2. Возврат к шагу 2.

**Приоритет:** Средний | **Частота:** Умеренно | **Сложность:** Низкая

## UC-007 Добавить контент

**ID:** UC-007  
**Название:** Добавить контент  
**Акторы:** Администратор  
**Уровень:** Пользовательский  

**1. Краткое описание:**  
Администратор добавляет новую запись об игровом объекте в информационную базу приложения через REST API.

**2. Предусловие:**
- Администратор авторизован (JWT с ролью ADMIN).
- Сервер доступен.

**3. Постусловие:**
- Новая запись сохранена в базе данных PostgreSQL.
- Версия данных обновлена (для синхронизации клиентов).

**4. Основной поток:**
1. Администратор инициирует добавление контента (POST-запрос к API).
2. Администратор передаёт данные нового объекта.
3. Администратор подтверждает добавление.
4. Система валидирует входные данные.
5. Система сохраняет запись в БД.
6. Система обновляет метку версии данных.
7. Система возвращает подтверждение с ID созданного объекта.

**5. Подпотоки:**

*A: Добавление через форму (если реализован admin-UI)*
- A1. Администратор заполняет веб-форму.
- A2. Переход к шагу 4 основного потока.

*B: Добавление через прямой API-запрос*
- B1. Администратор формирует JSON-тело запроса.
- B2. Отправляет POST /api/content с Bearer-токеном.
- B3. Переход к шагу 4 основного потока.

**6. Потоки исключений:**

*E1: Некорректные данные*
- E1.1. На шаге 4 валидация обнаруживает ошибки в полях.
- E1.2. Система возвращает 400 Bad Request с описанием ошибок.
- E1.3. Возврат к шагу 2.

*E2: Сервер недоступен*
- E2.1. На шагах 4–6 возникает серверная ошибка.
- E2.2. Система возвращает 500 Internal Server Error.
- E2.3. Прецедент завершается неудачей.

**Приоритет:** Высокий | **Частота:** Часто | **Сложность:** Средняя
