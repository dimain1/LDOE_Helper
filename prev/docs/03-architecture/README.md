# 03-architecture

## Диаграмма зависимостей

Отражает взаимодействие между слоями через определённые интерфейсы.
Используются два вида связей:
- Сплошная линия - прямая зависимость, компонент использует интерфейс
- Прерывистая линия - частичная зависимость, компонент реализует интерфейс

## ADR-001: Выбор архитектурного паттерна (PCMEF)
### Статус
Принято

### Контекст
Мобильное приложение с UI (включая overlay), бизнес-логикой (события, уведомления) и данными. Требуется разделение ответственности и удобство поддержки.

### Решение
Использовать паттерн PCMEF (Presentation–Controller–Model–Entity–Framework).

### Обоснование
- Чёткое разделение UI, логики и данных
- Упрощает тестирование и поддержку
- Подходит для нескольких интерфейсов (приложение + overlay)

### Последствия
- Повышенная сложность структуры

### Альтернативы
- MVC — слабое разделение логики
- MVVM — фокус на UI, менее явно выделена бизнес-логика
- Clean-achitecture - слишком избыточно по сложности

## ADR-002: Выбор базы данных (PostgreSQL)
### Статус
Принято

### Контекст
Необходимо хранить структурированные данные (контент, события) и их связи, с возможностью расширения.

### Решение
Использовать PostgreSQL.

### Обоснование
- Поддержка связей (реляционная модель)
- JSON (JSONB) для гибких атрибутов
- Надёжность и зрелость

### Последствия
- Требует настройки
- Сложнее чем SQLite

### Альтернативы
- SQLite — проще, но плохо подходит для серверной части
- MongoDB — гибкая, но сложнее с отношениями
- MySQL — аналог PostgreSQL, но менее гибок в работе с JSON

## ADR-003: Выбор механизма аутентификации и авторизации (JWT)
### Статус
Принято

### Контекст
Нужно реализовать аутентификацию и разграничение ролей (User/Admin).

### Решение
Использовать JSON Web Token.

### Обоснование
- Stateless (нет хранения сессий)
- Удобен для мобильного клиента
- Позволяет передавать роль пользователя

### Последствия
- Сложнее отзыв токенов

### Альтернативы
- Session-based — требует хранения сессий
- OAuth 2.0 — избыточен
